### Root Cause FOUND: tree-sitter match ordering in parse-worker.ts

**The captures.ts dedup IS working** — confirmed by direct test with `emitTsScopeCaptures()`. Only `@declaration.function` appears, `@declaration.variable` is correctly suppressed.

**The parse-worker.ts dedup (`processedDefinitionNodes`) FAILS** because tree-sitter `.matches()` returns `@definition.const` matches BEFORE `@definition.function` matches for the same code:

For `export const createTeamWorkflow = (db) => async (input) => {}`:
```
1. definition.const  → export_statement  (startIndex=0)  ← FIRST
2. definition.const  → lexical_declaration (startIndex=7)
3. definition.function → export_statement  (startIndex=0)  ← AFTER
4. definition.function → lexical_declaration (startIndex=7)
```

The `processedDefinitionNodes` Set is EMPTY when Const captures are processed. Function captures add to the set later — too late.

**Confirmed by running parse worker on test file:** Graph has BOTH `Const:/test/workflow.ts:createTeamWorkflow` AND `Function:/test/workflow.ts:createTeamWorkflow`.

### Key Architecture Findings

1. **`registry-primary-flag.ts` was DELETED by upstream** (commit `083aedbc` / RING4-1 #942). The concept of migrated/non-migrated languages is GONE. ALL languages now use the unified pipeline.

2. **`selectNodeBearingDef` in `scope-extractor.ts` (lines 808-817)** is upstream's solution for this exact problem, but it's a **DEAD EXPORT** — "No production call site yet" (line 803). Tracked by #1876 (deferred node-creation migration). Not active.

3. **Graph nodes are created ONLY in parse-worker.ts** from `tree-sitter-queries.ts` captures. The scope-resolution pipeline (`scope-resolution/graph-bridge/`) only calls `graph.addRelationship` (edges), never `graph.addNode`.

4. **Both paths run in parallel:** parse-worker creates nodes from legacy tree-sitter-queries.ts, AND captures.ts feeds the scope-resolution pipeline. Our captures.ts dedup works; the parse-worker dedup doesn't.

5. **The merge commit `3a9e4e9d`** removed our older parse-worker dedup block (which used number keys) believing upstream's version (string keys) was equivalent. Upstream's version has the same ordering bug.

### The Fix (same approach as captures.ts pre-pass)
Add a pre-pass to parse-worker.ts that collects all `@definition.function` startIndexes into `processedDefinitionNodes` BEFORE the main loop. Then Const captures will find the function startIndexes already in the set and be skipped.
